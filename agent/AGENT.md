# 打工人小账本 Agent

## 职责

这个 Agent 只负责两类工作：

1. 把用户的自然语言整理成可编辑的收支草稿。
2. 基于账本上下文回答收支、结余和分类问题。
3. 定位用户明确指向的近期流水，提出可审核的纠错建议。

Agent 不直接写入、修改或删除正式流水。新增、修改和删除都必须经过软件界面中的明确确认动作。

## 执行链路

```text
用户输入
  -> deterministic preprocessor（脚本抽取金额、日期、语义线索）
  -> Agent skill 选择
  -> 模型生成结构化草稿、纠错建议或回答
  -> validate_transaction_drafts / search_transactions tool 校验完整性
  -> 模型根据校验结果修正一次
  -> JSON 返回前端
  -> 用户审核后写账
```

## Agent 原则

- 金额、笔数和日期不能猜测；候选金额必须全部覆盖。
- “退款、退回、返款、返现”默认是收入中的“报销退款”，不能进入工资收入。
- 明确的账户转账不计入收入或支出。
- “工资卡”是账户，不等于工资收入；只有“工资到账”等语义才是工资。
- 购物、超市、家居、清洁、燃气等日常购买优先归入“日用”；餐饮、交通、订阅等使用对应分类。
- 返回的草稿必须包含类型、金额、分类、账户、发生时间和备注。
- 纠错返回 transaction_update，必须包含唯一流水 ID 和至少一个明确的新字段。
- 不能声称已经入账，不能返回 Markdown 代码块，不能把思考过程展示给用户。

## ReAct 边界

使用受控的 Reason-Act-Observe 循环，而不是无限自主代理：记账请求最多一次“模型草稿 -> 校验工具 -> 模型修正”，查询请求最多一次查询工具调用。工具均为只读工具，单次请求最多两轮工具交互，以保证响应速度和可审计性。

## 能力范围

- `search_transactions`、`analyze_spending_habits` 和 `get_user_preferences` 都是只读工具；纠错时先查找，再提出 transaction_update。
- 消费习惯分析优先使用本地聚合事实；外部模型不会自动获得完整历史流水。
- 偏好只能作为 `memory_suggestion` 返回，前端展示确认卡片后才保存。
- `agent/schemas.mjs` 对最终 JSON 做统一结构、字段、金额覆盖和转账完整性校验。
